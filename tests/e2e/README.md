# Сквозной тест перевода (без микрофона и динамиков)

Тест подаёт записанные фразы в настоящий конвейер движка так, как это сделал бы
микрофон, и проверяет всё, что получилось на выходе. Участие человека не нужно:
запуск, оценка и отчёт делаются одной командой.

```
WAV-файл ──inject_audio──▶ [ audio_engine.exe: STT → перевод → TTS ] ──▶ события и озвучка
                                                                          │
   сверка вне движка: Deepgram (эталонная расшифровка), Yandex/Groq (обратный перевод, судья)
```

* `outgoing` – ваша речь (`ru`) → перевод и озвучка на `en` (то, что услышит собеседник).
* `incoming` – речь собеседника (`en`) → перевод и озвучка на `ru`.

## Запуск

```bash
# 1. один раз: собрать движок (нужен MSVC, см. ниже)
cd native/audio_engine && cargo build --release --bin audio_engine && cd ../..

# 2. проверочный набор из синтетических фраз (голоса Windows)
python tests/e2e/make_synthetic_fixtures.py
python tests/e2e/run_e2e.py --phrases tests/e2e/phrases.synthetic.json

# 3. ваши фразы
python tests/e2e/run_e2e.py --phrases tests/e2e/phrases.json
```

Полезные ключи: `--only ru-01 en-02`, `--direction outgoing`, `--stt-provider auto`,
`--utterance-end-ms 500`, `--skip-back`, `--skip-ref-asr`. Код возврата: `0` всё прошло,
`1` есть проваленные фразы, `2` не поднялась инфраструктура (нет ключей, не запустился движок).

Отчёт: `tests/e2e/results/<время>/report.md` (и `report.json`). Рядом лежат озвучка движка
(`tts/*.wav`) и его журнал (`engine_*.stderr.log`, ключи в нём вычищены).

## Как записать фразы

* 5 фраз на русском (`outgoing`) и 5 на английском (`incoming`), по одной мысли в файле, 3–10 секунд.
* Любой формат, который читает ffmpeg (wav, m4a, mp3, ogg): раннер сам приведёт к 16 кГц моно.
* Полсекунды тишины в начале и в конце, тихая комната, говорите как на звонке.
* Файлы положите в `tests/e2e/fixtures/user/` (папка не попадает в git).
* Опишите их в `tests/e2e/phrases.json` по образцу `phrases.example.json`:
  `text` – что вы реально сказали (по нему считается точность распознавания),
  `expected` – желаемый перевод (необязательно, нужен для сравнения с эталоном).
  Если `text` пропущен, эталоном станет расшифровка Deepgram, и отчёт пометит это как непроверенное.

Если записывать нечем, озвучьте тексты голосами Windows (русский Microsoft Pavel, английский
Microsoft Mark): `python tests/e2e/make_synthetic_fixtures.py --manifest tests/e2e/phrases.json`
создаст файлы по путям `audio` из манифеста. Это синтетика, не ваш голос.

## Что проверяется

| Проверка | Как считается | Порог |
|----------|---------------|-------|
| Распознавание (STT) | доля сказанных слов в расшифровке движка | ≥ 0.80 |
| Эталонная расшифровка | Deepgram по тому же файлу: годна ли запись | справочно |
| Перевод | LLM-судья 1–5 (Groq), иначе chrF к `expected` | ≥ 4 / ≥ 0.45 |
| Озвучка (TTS) | озвучку расшифровывают заново и сверяют с текстом перевода (WER) | ≤ 0.30 |
| Обратный перевод | расшифровку озвучки переводят назад и сверяют со сказанным | судья ≥ 4 / chrF ≥ 0.40 |
| Задержка | конец речи → конец озвучки | ≤ 15 с |

Пороги лежат в `Thresholds` (`e2e/runner.py`). Раннер сам выбирает рабочую модель Groq из
`GROQ_CANDIDATES` (`e2e/providers.py`); если ни одна не отвечает, судьи отключаются, а
смысловые вопросы попадают в раздел «Needs review» отчёта.

## Поток, как у микрофона

Живой микрофон не замолкает между фразами. Поэтому `inject` непрерывно подаёт тишину и
вставляет фразы в этот поток. Без этого (поток обрывался после каждой фразы) Deepgram делил
все фразы, кроме первой, на паузе и иногда ошибался в первых словах, и в отчёте появлялись
«дефекты» движка, которых в реальности нет.

## Зонд распознавателя

`probe_stt.py` отправляет те же записи в Deepgram теми же параметрами, что и движок, и
печатает, что вернула каждая модель. Им сравнивают `nova-2-general` и `nova-3` и отличают
ошибку распознавателя от ошибки конвейера:

```bash
python tests/e2e/probe_stt.py --phrases tests/e2e/phrases.json --only ru-02 \
    --models nova-2-general nova-3 --repeat 10
```

## Склейка коротких фрагментов

Фрагмент короче двух слов («Привет,») не озвучивается отдельно: он ждёт продолжения, пока
слышна речь, и отпускается через 0,7 с тишины (не дольше 4 с). Для однословного ответа
это +0,45 с. Выключить: `TRANSLATOR_MIN_SEGMENT_WORDS=1`. Для проверки в манифесте есть
`ru-01p` (запись `ru-01` с паузой 450 мс после первого слова).

## Ограничения

* Синтетические голоса чистые и ровные: на них результат – потолок, а не замена живой речи.
* Обратный перевод смешивает ошибки STT, перевода и озвучки. Провал нужно читать вместе с
  подробностями фразы в отчёте: что услышано, что переведено, что произнесено.
* Однословная озвучка (0,3 с) почти не распознаётся повторно, поэтому проверка озвучки для таких фраз
  ненадёжна. Первое слово короткой озвучки иногда не распознаётся Deepgram nova-3. Поэтому клип
  дополняется тишиной, а при пустом ответе проверка повторяется на nova-2.
* Тест обращается к Deepgram, Groq и Yandex под вашими ключами из `.env` / `settings.json`
  (приоритет у `settings.json`, как в приложении). Ключи нигде не печатаются.
* Пары языков – только `ru`/`en` (в движке есть голоса Piper для них).

## Зачем в движке `inject` и `null`

`TRANSLATOR_MIC_DEVICE`/`TRANSLATOR_MEET_INPUT=inject` включают виртуальный вход, а
`TRANSLATOR_SPEAKER_DEVICE`/`TRANSLATOR_MEET_OUTPUT=null` – приёмник без звука
(`native/audio_engine/src/audio/inject.rs`). Звук движок отдаёт событием `tts_audio`.
В обычном режиме ничего не меняется.

## Сборка движка на Windows

Нужны Visual Studio Build Tools 2022 с компонентом «Разработка классических приложений
на C++» (MSVC и Windows SDK). Сборку запускайте из окружения `vcvars64.bat`, иначе
`cargo` подхватит чужой `link.exe` из Git Bash:

```bat
call "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvars64.bat"
cargo build --release --bin audio_engine
```

Для локальной модели перевода (фича `local-mt`, CTranslate2) нужны два отличия. Сборка идёт из
короткого каталога, иначе MSVC не создаёт лог-файлы на длинном пути worktree, и с статическим CRT,
который требует крейт `ct2rs`:

```bat
set "CARGO_TARGET_DIR=C:	\lm"
set "RUSTFLAGS=-C target-feature=+crt-static"
cargo build --release --features local-mt --bin audio_engine
```

Без `RUSTFLAGS` линковка падает с LNK2038. Загрузка самой модели этими тестами не проверяется:
нужны файлы `model.bin`, `source.spm` и `target.spm`.

## Оценка промпта Groq

`tests/e2e/prompt_eval.py` прогоняет 28 фраз (RU→EN и EN→RU, с эталонами) через кандидатов
промпта и выводит среднюю оценку судьи, долю оценок ≥ 4 и задержку. Кандидат `file` берёт
текст из `native/audio_engine/src/translation/groq_prompt.txt`, тот же файл, что и движок:

```bash
python tests/e2e/prompt_eval.py --candidates file yandex --repeat 2 --show --out tests/e2e/results/prompt.json
```

Запросы идут последовательно с паузой, потому что Groq отвечает 429 при параллельной нагрузке.
Колонка `unjudged` показывает ответы без оценки судьи: средние по ним не считаются.
